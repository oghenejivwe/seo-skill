# Phase 2 — Architecture

Goal: `seo/structure.yaml` — the page plan, and the source of truth for internal linking for the life of the project.

This is the phase where mistakes get expensive. Content can be rewritten. URLs, once indexed and linked, cannot be changed without losing something.

---

## One cluster, one intent, one page

Each cluster from phase 1 becomes exactly one page. That page targets the whole cluster — potentially hundreds of queries — not just the head term.

The failure mode on one side is a page per keyword, which was how this worked fifteen years ago and now just produces thin pages competing with each other. The failure mode on the other side is one page covering several intents, which satisfies none of them and loses to pages that commit.

**Most keywords don't produce a page at all.** The keyword set has no cap, but by the time it reaches this phase each keyword carries a `role` and a `target_url`. Only `primary` roles create pages. Keywords tagged `faq` and `section` attach to a page that already exists, as a question heading or a section heading. A new page is warranted when a keyword's results don't overlap any existing page's results — not when it's merely a different phrasing.

This is how a list of several thousand keywords turns into a few dozen pages rather than a few thousand.

## Declare the URL pattern once

Pick a pattern and never deviate:

```
/<category>/<item>
/<item>/<modifier>
/compare/<a>-vs-<b>
/integrations/<service>
```

Which pattern you choose matters far less than whether you stick to it. Arguments about whether the category or the qualifier comes first are not worth having; inconsistency is what actually costs you, because it breaks the hierarchy signal and makes every future decision a judgement call.

Rules that do matter:
- The primary keyword appears in the URL
- Hyphens, never underscores — Google reads hyphens as word separators and underscores as nothing
- Short. Drop filler words that carry no meaning
- No IDs, dates, or query strings in anything you want ranked
- Lowercase, no trailing variation

## Page types

Most projects need some subset of these. Name them explicitly in the structure file, because the type determines the content contract in phase 3 and the schema in phase 4.

| Type | Intent | Job |
|---|---|---|
| `home` | navigational + category | Say what this is in the first screen |
| `product` / `feature` | commercial | Convert. One feature, one page |
| `pricing` | transactional | Convert |
| `comparison` | commercial | "x vs y" — high intent, usually under-served |
| `alternative` | commercial | "alternative to x" — people actively leaving a competitor |
| `integration` | commercial | One per service you connect to |
| `use-case` | commercial | One per job-to-be-done |
| `guide` | informational | Build topical depth, link down to money pages |
| `glossary` | informational | Cheap, and it owns your entity vocabulary |
| `tool` | transactional | Calculators and generators. AI can't answer these, and they attract links |
| `docs` / `help` | informational | Badly under-used. See `08-aeo.md` |

For a pre-launch project, the order of value is roughly: product and pricing first, then comparison and alternative, then integration and use-case, then guides. Comparison and alternative pages punch above their weight because the searcher has already decided to buy something and is only choosing between options.

## Hierarchy and linking

```
home
 └── category / hub
      └── page
           └── supporting page
```

Two rules that between them prevent most structural problems:

**Links are generated by walking `structure.yaml`.** Never by asking a model which pages seem related. Models link things that are topically similar, which produces a web rather than a hierarchy — and the hierarchy is what search engines and AI systems use to work out what the site is about and which pages matter.

**Editorial links beat navigation links.** A link inside a sentence in body copy carries weight. The same link in a nav bar or footer carries almost none, because it's site furniture rather than a recommendation. So each hub page should mention each of its children in prose, with the link in that prose.

Keep anything important within three clicks of the home page, and make sure every page has at least one inbound internal link — an unlinked page is invisible to crawlers that arrive by following links.

## Avoid planning two pages for one intent

Before adding a page, check it against the existing plan: if another page already owns that intent, you're planning cannibalisation. Two of your own pages competing for one query splits the signal and usually means neither ranks.

The tell at this stage is two clusters whose SERP results overlap heavily. If they do, they were one cluster.

## Output

```yaml
# seo/structure.yaml
site: https://example.com
url_pattern: "/<category>/<item>"

pages:
  - url: /
    type: home
    primary_keyword: <cluster head>
    title: <= 60 chars, keyword front-loaded
    h1: mirrors the title
    cluster: <cluster id from keywords.csv>
    parent: null
    links_to: [/features/thing, /pricing]
    schema: [Organization, WebSite]

  - url: /features/thing
    type: feature
    primary_keyword: ...
    secondary_keywords: [...]
    title: ...
    h1: ...
    cluster: ...
    parent: /
    links_to: [/compare/thing-vs-other]
    schema: [SoftwareApplication]
    status: planned        # planned | drafted | reviewed | live
```

`status` makes the file resumable. A later run reads it and knows what's left.

## Before moving on

Show the user the full page list with the URL, the intent it owns, and the traffic potential behind it. This is the last cheap moment to say "we don't need that one" or "where's the page for X".
